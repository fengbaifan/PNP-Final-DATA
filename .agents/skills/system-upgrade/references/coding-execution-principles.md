# 编码执行原则（Coding Execution Principles）

> 本文定义仓库级编码执行原则。
> 它约束代码与规则修改时的工作方式，但不替代具体 skill 的阶段契约，也不覆盖领域级事实判断。

## 一、适用范围

适用于以下场景：

- 修改 `scripts/`、规则文档、运行治理文档与知识库支撑代码
- 调整 `AGENTS.md`、`README.md`、`SKILL.md`、`references/*.md`
- 执行需要读取上下游、保持最小改动和显式验证的多步任务

不适用于以下场景：

- 替代 ingest / verify / quality / growth 的领域语义裁决
- 定义模型厂商、会话令牌或平台专有限制
- 覆盖已有 skill contract 中更具体的输入、输出、门禁与失败状态

## 二、核心原则

1. 先思考，再编码。
   在开始修改前，先说明目标行为、验收条件、当前不确定点、必要假设和关键取舍；不能确认的地方应显式标出，不得静默假设。存在更简单方案时，应先提出并比较。

2. 简单方案优先。
   使用解决当前问题所需的最少代码和规则；不得增加想象中的功能，不得为一次性逻辑设计抽象层。

3. 保持手术式修改。
   只修改达成目标所必需的文件和片段；不得借机优化、重构、重排或格式化邻近区域。

4. 以成功标准驱动迭代。
   先定义成功结果，再按“修改 -> 最近邻验证 -> 状态复述 -> 下一步”循环推进。不得用逐条操作指令替代成功标准，也不得从无法清楚复述的状态继续扩张范围。

5. 语言模型只承担语言任务。
   语言模型可用于分类、起草、摘要和从非结构化文本中抽取信息；路由、重试、状态码处理和确定性转换应交给常规代码。状态码已经回答的问题，不得再交给模型判断。

6. 显式声明并遵守执行预算。
   执行环境应在开始前声明任务预算和会话预算。接近预算边界时，先总结当前状态并重新开始，不得静默超限。具体模型厂商、计量方式和预算数值由项目级覆盖规则定义。

7. 暴露冲突，不做折中混写。
   如发现冲突模式，应选取当前活跃、较新或验证更充分的一种，说明选择理由，并记录另一种待清理；不得把两套规则平均化后混合使用。

8. 先读后写。
   修改前至少读取目标文件、直接调用方或直接依赖的共享规则；若仍无法解释当前组织方式，应先补足上下文，再决定是否修改。

9. 测试必须表达行为价值。
   测试不是完成目标本身。每个测试都应说明为什么该行为重要，并在业务逻辑变化时失败；不得用只复述硬编码输入输出的测试制造虚假覆盖。

10. 长任务保留检查点。
    多步任务在阶段结束时应能清楚复述：已完成什么、验证了什么、还剩什么；若无法复述当前状态，应先收敛范围再继续。

11. 约定优先于新颖性。
    命名、结构、文档层级、字段写法和验证顺序优先沿用仓库现有约定。若认为现有约定有害，应显式提出，不得静默创建分叉模式。

12. 显式失败，不得静默失败。
    不能确认成功时，不得宣称完成；跳过的记录、测试、边界和残留不确定性必须直接暴露。未验证的部分不得写成已通过。

13. 清理执行副产物。
   脚本运行产生的 `.bak`、`.tmp`、临时扫描脚本或一次性中间文件，不得在任务结束后继续留在知识元目录或主工作树中；若因回滚或追溯需要暂时保留，必须明确其身份与后续清理动作。

## 三、落地边界

- `AGENTS.md` 只保留一句摘要性入口，例如“编码执行遵循最小改动、先读后写、状态诚实、显式验证；细则见本文件”。
- 具体阶段约束仍应写在对应 `SKILL.md` 或 `references/*.md`，不得把本文件当作通用兜底来覆盖更具体规则。
- 与特定模型、厂商、会话预算绑定的约束，不进入本文件；只有影响仓库执行事实的规则才可沉淀为系统规则。
- 当本文件与更贴近执行位置的具体契约冲突时，以后者的具体约束为准，但冲突必须回写 system-upgrade 记录。

## 四、验收关注点

落地该原则时，至少检查以下问题：

- 入口文档是否仍保持摘要，而非重新膨胀为规则手册
- 细则是否位于 `system-upgrade/references/` 或更贴近执行的位置
- README 与 AGENTS 是否指向同一权威落点
- 规则是否保持模型无关，并避免复制 skill 层细则
- 项目级模型和预算配置是否留在领域覆盖层，而非反向写入系统级原则
- 修改后的任务是否保留明确验证与未验证说明

## 五、直接落点

- 当任务是实际执行代码或规则修改时，本文件提供仓库级行为原则。
- 当任务是审查一次实现是否遵守这些原则时，使用 `.agents/skills/inspector/SKILL.md` 的 `compliance` 模式。
- 若后续新增更贴近某个 skill 的实现清单，应优先写到该 skill 的 `references/`，而不是继续扩写本文件。
- 当任务涉及批量脚本写回时，还应复查是否产生了新的备份文件或临时产物，并在最终验证前清零这些噪音文件。
