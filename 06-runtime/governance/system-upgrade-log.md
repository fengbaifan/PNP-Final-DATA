## REV-009：知识发现与涌现机制的理解纠正（2026-09-09，审读记录）

### 核对发现

- domain-registry.md 把项目名称预先设为 Domain，并要求 5 个 pilot 维度中至少 3 个晋升 core；dimension-registry.md 预先设计 A–E 五个维度，并按数量与不可归类条件决定新增结构。
- workflow-overrides 和 synthesize 优先要求知识进入已有结构；这实际偏向维护预设分类，而非从材料中生成结构。将预设改称 pilot 并未消除这一偏差。
- 磁盘 10 个试点 KU 均已填写 primary_domain 和 A–E 中的 primary_dimension，而 structure 的四类正式节点尚未 materialize。这些字段反映先前分类安排，不能作为经过知识涌现形成结构的证据。
- 先前机械测试只证明路径、格式及既有契约一致，没有验证这套机制是否符合用户研究意图；此前系统完成结论不包含本次确认的概念纠正。

### 修正后的机制理解（Agent 解释，以用户 REV-009 为依据）

可以约定 KU、Topic、Theme、Dimension、Domain 的表达层次，但各层具体内容、名称、数量、边界和成员应由知识分析形成。生成方向为 KU 及其有证据关系 → Topic → Theme → Dimension → Domain。成果形成后才可按反向层级导航展示，不能把展示顺序当作发现顺序。

涌现不是把对象装进更大的集合，而是在下层对象的关系中辨认上层才显现的语义组织：KU 之间呈现具体问题或模式，形成 Topic；Topic 之间的关联与差异形成 Theme；Theme 之间形成可解释的分析维度；Dimension 之间形成较完整的问题领域。每次提升均应解释成员为什么共同成立、形成了什么新的组织或解释意义、适用边界及不确定性，并能追溯下层证据。不能以共现、相同标签或固定数量替代这些判断，也不能以涌现为名新增无来源的事实断言。

发现是识别、提出、比较和检验新联系与解释的研究活动；涌现是其中逐级形成知识组织与高层意义的机制。层级产出是可审查的研究结果，后续知识增长可能修订、拆分或推翻它；无需填满每一层，也不要求每个 KU 有唯一归属。新材料与反例可反馈到下层重新审查，但不能从既有上层标签倒推出材料事实。

第一部分仍按摄入—处理—知识元—对齐—补足—关系执行，为第二部分积累可追溯材料与关系。第二部分启动后才正式开展涌现分析及发现；当前不为凑齐 Topic、Theme、Dimension、Domain 制造内容。允许摄入前确定材料范围、来源版本和问题背景，但项目名称、书名或取材边界不能直接充当已经涌现的 Domain。

### 最小交接与空项目验收标准

每次交接至少能回答：本次对象与范围是什么；依据哪个输入版本；实际做了什么；当前成果在哪里；哪些已成立、哪些仍不确定或受阻；下一环节可处理哪些对象及为何。用同一对象现有过程/结果文档表达，不为这些问题再建六份表。

可以事先定义功能、对象基本表达方式、来源证据要求、稳定标识、状态、输出位置和交接边界。不能事先定义具体知识元、Topic/Theme、维度/领域名称与数量、归属、关系、发现结论、验证日期、完成率或成果规模。常用类型与关系词表属于表达规则，不等于已有研究内容；应允许有依据的扩展，避免为填词表制造实例。

空项目应能停留在“尚未执行”，没有来源/知识/结构/页面时既不伪造数据也不报应立即填满的缺口。首次收到明确执行任务后才形成对应对象工件；一般规则仍可提前完整。默认不为固定规模、篇幅、满层级、全库外部核验或满健康分数新增步骤。

推荐修订顺序：先统一 AGENTS 的空项目定位和涌现方向，再补全 pipeline 的两部分与交接/回退，随后修订八个 Skill 及直接模板/字段，最后对齐实际使用的辅助代码和空状态检查。保留八个 Skill，不再拆增同用途技能。

## REV-011：门禁、审核和冗余审查补充（2026-09-09）

### 结论与证据

存在过度设计，主要在把批量自动化、历史兼容和多工件追溯要求放进日常语义工作的默认路径；不在六个业务阶段或八个 Skill 的数量本身。还存在相反的问题：第二部分的语义功能与交接不够具体。应同时做“执行负担减法”和“语义职责补全”，不能把文档越短等同于系统越好。

现行 AGENTS/pipeline 已明确阶段交接不自动增加用户审批，runtime-state-machine 也已规定短任务不必创建状态文件。因此不能宣称当前每一步都要求用户批准，也不应为精简删除已明确按需的恢复和证据保护。

具体冗余或不适配：

- 日常写回在 work-package、verify/relate Skill 和 relation-governance 中反复铺设 candidate → approved → exact plan → dry-run → apply → validation → result；重复的是合同描述及要求分别固化多个工件，不是来源证据和判断责任本身。单条语义修订可以在既有过程记录中说明依据、直接更新授权范围内的固定成果并定向核对；批量机器写回、身份合并、覆盖多对象等才需要独立计划/预检/恢复资料。
- compact-v4 的 summary、业务 results/stages、工作包 summary、apply result 都可能叙述同一结果。应指定业务 results 为人工交接入口；必要机器结果只存执行事实并被链接引用，兼容摘要不再复制一套人工报告。
- candidate、decision、review_queue、defer_queue、阶段状态及 file_back_status 分属不同用途，当前容易被误用为每个对象必走的多轮审批。应明确同一判断只作一次；对象阶段状态说明业务进度，候选状态只用于真实候选流转，机器队列仅是执行视图，输出回流仅在有问题/增量时启用。
- 六阶段不是六轮重复审核。成稿判断对象边界与来源支持；对齐检查身份和冲突；补足解决明确缺口；关系检查具体断言，inspector 只做有目标的检查，不逐阶段再走一遍所有步骤。新证据、冲突或范围变化才重开对应问题。
- upgrade-acceptance-gates 的 generated_clean 仍要求生成投影相对 HEAD 无漂移，与 AGENTS/pipeline 对未提交修改采用哈希幂等的边界不一致；分类 README 要求也已过时。应以实际受影响内容的正确性检查为准，提交基线核验留在已授权交付时。
- 高文档版本、旧模型/项目样例和大量历史兼容解释不应占据空项目主流程。当前规则讲清现在如何执行，历史沿革只留既有日志；机器协议兼容需要单独保留，不未经检查重编号。
- 预设维度、固定晋升数量和层级完整度要求是研究偏置，不能保留为所谓质量门槛。涌现取决于语义与证据，不取决于凑满分类或健康分数。

### 保留与条件启用

日常基本路径：读输入及上一阶段结果 → 完成本阶段语义工作 → 保存过程/当前结果 → 核对直接受影响项 → 交接。检查可以并入工作本身，不另设审批阶段；阻断只针对依赖不成立的具体对象。

必须保留：来源可定位、原始材料不被误改；同一对象的身份/版本准确；事实与关系有对应证据；不伪造已完成或已验证；正式成果唯一；变更可追溯。保留这些基本条件不意味着固定多人复核或用户逐步批准。

按条件启用：外部核验只针对必要问题；完整冲突裁决只针对真实冲突；独立审查只在任务和证据要求下采用；机器批量写回使用预检及可恢复提交；长任务启用状态文件；脚本/schema 修改运行相应回归；索引与页面在其输入实际变化、交接需要时刷新。已确认材料不因重复运行而反复审查。

不作为默认动作：每阶段全套测试、全库外部采集、所有索引刷新、固定审核轮数、强制完整层级、为空状态填数据、为通过 HEAD 检查自动提交、为每次小修改生成 plan/summary/report 副本。

### 页面保留与数据更新

用户允许保留现有视觉样式、布局、颜色、字体及适用交互，不要求重新设计页面。具体内容必须读本项目的实际可用数据：节点与类型、正式关系、来源与证据状态、实际涌现的层级、数量统计、筛选选项和说明文案。项目尚未执行时呈现空状态，不用旧项目数据或示例数字装成新结果。

后续新数据产生后，保留样式并调整数据模型到页面的映射；无某层结构则不显示虚构分组，现有分组/筛选若依赖预设 A–E 则改为实际数据驱动。图中有关系不等于已形成 Topic，页面不能反过来要求知识填满预定布局。更新后检查空状态、真实统计、筛选、节点详情、关系与证据链接、已有视觉交互是否仍有效。
